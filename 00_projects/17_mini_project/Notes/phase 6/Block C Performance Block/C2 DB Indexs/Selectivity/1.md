### Selectivity, composite indexes, column order, write cost


### Selectivty

Selectivity: what fraction of the table a filter matches. 
Fewer matches means higher selectivity, and indexes help most there.

Query	Rows returned	Plan chosen	Time
isbn = ...	1	Index Scan	0.06 ms
author_id = 42	~121	Bitmap Index/Heap Scan	0.24 ms
available = true (2%)	~10,000	Index Scan	6.5 ms
genre = 'tech' (25%)	~125,000	Bitmap Index/Heap Scan	28 ms
available = false (98%)	~490,000	Seq Scan	63 ms


### Composite indexes

One index on multiple columns, 
sorted by the first column, then by the second within it, and so on.

i.e:
CREATE INDEX idx_books_author_created
ON books (author_id, created_at DESC);

all entries for author 42 are together, and within that group, dates are sorted newest to oldest.


Without the index, PostgreSQL might need to:
1. Search the table for books written by author 42.
2. Sort those books by creation date.

With the composite index, PostgreSQL can:
1. Navigate directly to the entries for author 42.
2. Read those entries in date order.
3. Retrieve the corresponding book records.


### Column Order Matters

An index on (A, B) works well for:

WHERE A = ?
WHERE A = ? AND B = ?
WHERE A = ? ORDER BY B

It is generally not good for WHERE B = ? alone, because B isn’t sorted globally, only within each A


### Read performance vs write cost

Every index is a separate sorted structure that must be updated on every INSERT, UPDATE (of an indexed column) and DELETE.

	                                Lab result
Insert 100k rows,                   PK index only	260 ms
Same insert with 4 extra indexes	1,607 ms (~6x)
Table size	                        60 MB
Each index	                        8 to 20 MB

add indexes for queries you actually run and need to be fast. Don’t add them “just in case.”

### Where to add

Read-heavy table (books catalog)  → more indexes are fine
Write-heavy table (audit log, loans being inserted constantly) → be selective
