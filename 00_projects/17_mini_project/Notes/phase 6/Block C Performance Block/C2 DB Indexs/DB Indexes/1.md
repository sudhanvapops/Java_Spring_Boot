### Index Scan

Index is a Seprate, sorted Data Structure
That maps Column values to row location

isbn    page, row 
98647   847, 12
98654   900, 98
99600   765, 45
99678   595, 34

An index scan does this:

Search the index for 98647
(fast, because the index is sorted)

Get the row location (page 847, row 12)
Jump directly to that page and fetch the row


instead of reading ~1 pages
u may read 3 to 4 index pages 
+ 1 table page

N+1 work (C1) was about how many queries you send. Indexes are about how expensive each one is. 
A fixed N+1 can still be slow if each query is a seq scan.


### But

PostgreSQL doesn't always need an index. 
Sometimes reading the entire table is faster than using an index.

sequential scan is not “bad.” If your query needs 60% of the table anyway, 
reading everything in order is actually the fastest plan, 
because sequential disk reads are cheap. 
The planner picks it deliberately in that case. We’ll come back to this when we hit selectivity.

If i have 1M records
and i want 60% of it in my result

Then A sequential read is much faster 


Index Scan:

Use the salary index

Find matching entries in the index, 
then retrieve the corresponding table rows.

Finds 600,000 entries, 
potentially performs many scattered table-page reads.

Because the matching rows may be spread across the table, 
retrieving them individually can be expensive.

### Why 

Suppose the table occupies 10,000 disk pages.
A sequential scan might read those 10,000 pages in order.


But an index scan could find 600,000 matching rows scattered throughout those same 10,000 pages.

Even though the index helps identify matching rows, PostgreSQL might still need to visit most of the table pages to retrieve the actual records.


So you pay for two operations:
1. Traversing the index.
2. Fetching the matching rows from the table.
