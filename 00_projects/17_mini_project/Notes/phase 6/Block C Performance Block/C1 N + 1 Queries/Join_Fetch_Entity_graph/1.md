### Mental Model

All Lazy and Fetch 
sets a default FETCH Plan
The same for every query 

the demand wont meet for a specific endpoint causing 1 + N Query problem


## FETCH JOIN

A fetch join overrides the default for a single query: 
    for this query, load these associations in the same SQL statement

so now instead of N + 1 trips we have 1 trip

so after data arrived
example: book.getAuthor() wont cost a qury since it is already in the Persistance context


Write your own Join query in JPQL

@Query(
        value = """
            SELECT br FROM BorrowRecord br
            JOIN FETCH br.borrowTransaction bt
            JOIN FETCH bt.member m
            JOIN FETCH br.book b
        """,
        countQuery = "SELECT COUNT(br) FROM BorrowRecord br"
    )
List<BorrowRecord> findAllWithAssociations(Pageable pageable);

### Enitty Graph

declarative, attached to a repository method. 
It lists the paths to fetch, and the query itself can stay simple or derived.

@EntityGraph(attributePaths = {"borrowTransaction", "borrowTransaction.member", "book"})
@Query("Select br from BorrowRecord br")
List<BorrowRecord> findAllWithGraph();


### DTO Projection

it is fastest
and it doesnt need to hold alll the context in memory 
like if we want only one or two fields from that enitty
we dont need to query them all

instead we can make a Dto for it 
and just write a sql query to join and fetch only that fields 

So when the intention is only to Read them 
use this method 
to save memory and make the response fast

A DTO projection tells the database: “give me exactly these columns, shaped like this object.” No entities are built, nothing goes into the persistence context, and there are no lazy proxies. 
Because no entity graph exists, there is nothing to lazy-load, so N+1 can’t happen at all.

Because no entity graph exists" means: You don't need a map or a fetch plan because there are no hidden relationships to solve.


The time is drastically reduce for 100k record from 5 secodns -> 2 seconds(warmp included) -> 1.3s
