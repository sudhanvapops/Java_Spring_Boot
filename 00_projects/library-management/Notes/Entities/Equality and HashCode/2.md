### Id based implementation has a trade-off.

Before persistence: id is 0
after persistance id becomes lets say 10
hashCode changes 

Same problem again.


So Why Is This Still Used?
Because:
👉 For entities without business key, there is NO perfect solution.


So we accept:
ID-based equality works only after persistence
Avoid putting transient entities in hash collections


### BorrowRecord (Even More Subtle)

Can BorrowRecord use:
    borrower + book + borrowDate as equality?


But think deeper:
    What if same book borrowed twice?
    What if dates overlap?
    What if record updated?

Should BorrowRecord have business-key equality OR id-based equality?
id based

cause: If you tried a business key here, you’d quietly create duplicates or false equality over time.
