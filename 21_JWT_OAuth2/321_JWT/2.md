### Why HttpOnly cookies?

The browser stores the JWT automatically.
JavaScript cannot read it because of the HttpOnly flag.

Then every future request automatically includes

Cookie:
accessToken=eyJhbGc...

Your frontend never has to manually attach it.


That's why authentication is a trade-off

| Storage                      | XSS Risk | CSRF Risk                 |
| ---------------------------- | -------- | ------------------------- |
| localStorage + Authorization | High     | Low                       |
| HttpOnly Cookie              | Low      | Higher (without defenses) |


How do modern websites use cookies safely?
1. SameSite cookies
same-site=strict

2. CSRF Tokens

The server generates a random token.

Example:

Cookie:
session=abc123

HTML:

<input type="hidden"
       name="_csrf"
       value="x8FJ3..."
>

When the form is submitted:

Cookie: session=abc123
CSRF-Token: x8FJ3...

An attacker on another site can cause the browser to send the cookie, but they cannot read your page to obtain the CSRF token (thanks to the browser's same-origin policy). The server checks that both the session and CSRF token are correct before accepting the request.


### What do most production applications do?

A common pattern today is:

1. Access token: short-lived (5–15 minutes), stored in an HttpOnly, Secure cookie.
2. Refresh token: longer-lived, also in an HttpOnly, Secure cookie, often rotated after use.
3. CSRF protection: SameSite=Lax or Strict where possible, plus CSRF tokens or Origin checks for sensitive operations.




### Think of it like this:

1. Cookie authentication: "The browser automatically carries my ID card everywhere." Convenient, but you need guards (SameSite, CSRF tokens, Origin checks) to prevent someone else from tricking the browser into using it.

2. Authorization header authentication: "I take my ID card out of my wallet and hand it over manually." That avoids automatic sending (and thus classic CSRF), but if someone steals your wallet (through XSS), they have the ID card.
